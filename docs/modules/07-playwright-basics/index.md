## Почему Playwright важен для Automation QA

Playwright позволяет автоматизировать действия в браузере. Тест взаимодействует со страницей почти как пользователь: переходит по адресу, нажимает ссылки, заполняет поля и проверяет результат. Встроенное автоматическое ожидание помогает не выполнять действие раньше, чем элемент будет готов. Playwright также поддерживает снимки экрана, trace и отчёты, которые помогают анализировать падения. TypeScript и Playwright — распространённый набор технологий для современной автоматизации UI.

## 1. Что такое Playwright test

Тест Playwright — это файл TypeScript, в котором описаны действия в браузере и ожидаемый результат.

```ts
import { expect, test } from '@playwright/test';

test('Playwright homepage has correct title', async ({ page }) => {
  await page.goto('https://playwright.dev/');

  await expect(page).toHaveTitle(/Playwright/);
});
```

В этом примере:

- `test` создаёт тест;
- название теста описывает ожидаемое поведение;
- `async` нужен, потому что действия в браузере асинхронны;
- `{ page }` предоставляет доступ к странице браузера;
- `await` дожидается завершения действия или проверки.

## 2. `test` и название теста

Название должно быть понятным и сообщать, что именно проверяется.

```ts
test('user can open Playwright homepage', async ({ page }) => {
  await page.goto('https://playwright.dev/');
});
```

Неудачные названия:

- `test('test1', ...)`;
- `test('check', ...)`;
- `test('page works', ...)`.

По таким названиям сложно понять причину падения в отчёте. Они также мешают ревьюеру быстро оценить назначение теста в PR.

## 3. `page`

Объект `page` представляет одну вкладку браузера. Через него тест может:

- открыть URL;
- нажать на элемент;
- заполнить поле;
- получить состояние страницы;
- проверить заголовок или URL.

```ts
await page.goto('https://playwright.dev/');
```

## 4. Открытие страницы через `page.goto`

Метод `page.goto` открывает страницу и возвращает Promise, поэтому перед вызовом используется `await`.

```ts
await page.goto('https://playwright.dev/');
```

Если в `playwright.config.ts` уже настроен `baseURL`, можно передать относительный путь:

```ts
await page.goto('/');
```

Абсолютный URL открывает точный адрес. Относительный URL работает только при настроенном `baseURL` и дополняет его переданным путём.

## 5. Простые действия

На этом этапе достаточно трёх действий:

- `click` — нажать на элемент;
- `fill` — заполнить поле;
- `press` — нажать клавишу.

```ts
await page.getByRole('link', { name: 'Get started' }).click();
```

```ts
await page.getByPlaceholder('What needs to be done?').fill('Buy milk');
await page.getByPlaceholder('What needs to be done?').press('Enter');
```

Здесь используются простые locators, чтобы найти элементы. Подробная стратегия выбора locators будет рассмотрена в модуле 08. Сейчас важнее понять последовательность: найти элемент, выполнить действие, проверить результат.

## 6. Простые проверки

Assertion проверяет, соответствует ли фактический результат ожидаемому.

```ts
await expect(page).toHaveTitle(/Playwright/);
```

```ts
await expect(page).toHaveURL(/.*intro/);
```

```ts
await expect(page.getByText('Buy milk')).toBeVisible();
```

`expect` выполняет проверку. Многие проверки Playwright автоматически ожидают нужного состояния в пределах установленного времени. Не заменяйте проверки одним `console.log`: вывод значения не сообщает test runner, прошёл тест или нет.

## 7. Первый полный тест

```ts
import { expect, test } from '@playwright/test';

test('user can navigate to Get started page', async ({ page }) => {
  await page.goto('https://playwright.dev/');

  await page.getByRole('link', { name: 'Get started' }).click();

  await expect(page).toHaveURL(/.*intro/);
  await expect(page.getByRole('heading', { name: 'Installation' })).toBeVisible();
});
```

Сценарий состоит из трёх частей: открыть страницу, выполнить действие пользователя и проверить ожидаемый результат.

## 8. Команды test runner

В репозитории домашних заданий могут быть подготовлены npm scripts:

```bash
npm run test
```

```bash
npm run test:headed
```

```bash
npm run test:ui
```

```bash
npm run test:debug
```

```bash

```

Те же основные операции можно запускать напрямую:

```bash
npx playwright test
npx playwright test --headed
npx playwright test --ui
npx playwright show-report
```

Если нужные npm scripts уже настроены, используйте их: так вся команда запускает тесты одинаково. Прямые команды `npx playwright ...` также допустимы.

## 9. Headless mode и headed mode

- В headless mode тесты выполняются без видимого окна браузера.
- В headed mode браузер открывается на экране.
- Headed mode удобен во время обучения и первичного поиска ошибки.
- В CI обычно используется headless mode.

Наблюдение за браузером помогает понять сценарий, но не заменяет анализ результата в терминале.

## 10. UI mode

UI mode позволяет интерактивно запускать тесты и изучать их шаги.

```bash
npm run test:ui
```

или:

```bash
npx playwright test --ui
```

Этот режим удобен для обучения и повторного запуска одного теста. При этом он не заменяет обычный запуск из терминала, который обязательно нужно выполнить перед PR.

## 11. Debug mode

Debug mode помогает медленно пройти сценарий по шагам и посмотреть состояние страницы.

```bash
npm run test:debug
```

или:

```bash
npx playwright test --debug
```

Пока достаточно знать назначение режима и уметь его открыть. Подробные приёмы отладки будут рассмотрены позже.

## 12. HTML report

После запуска Playwright может показать HTML report.

```bash
npm run report
```

или:

```bash
npx playwright show-report
```

Отчёт показывает прошедшие и упавшие тесты и помогает понять, что произошло. Каталоги с созданными отчётами не нужно добавлять в Git: их содержимое генерируется заново при запуске.

## 13. Trace Viewer: первое знакомство

Trace сохраняет информацию о ходе теста. Trace Viewer может показать действия, снимки экрана и временную шкалу, поэтому он полезен при поиске причины падения. На этом этапе достаточно познакомиться с интерфейсом. Настройка trace и более глубокая отладка появятся в следующих модулях.

## 14. Типичные ошибки начинающих

- забывать `await` перед асинхронным действием или проверкой;
- давать тестам неинформативные названия;
- писать тест без assertions;
- использовать `console.log` вместо проверки;
- полагаться на нестабильный текст или locator;
- добавлять `playwright-report` или `test-results` в Git;
- менять слишком много файлов в одном PR;
- запускать тесты только в UI mode и не проверять их из терминала.
